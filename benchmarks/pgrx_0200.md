Started: 2026-11-13T03:21:52.538843+00:00.

20,000 documents; 2,000 queries; 3 fresh rounds per variant.

All variants use the same PostgreSQL, pg_search, compiler, dictionaries and release flags.
Native library hashes, full scored hits, plans, warm/first-backend aggregates and pressure are retained in JSON.

PostgreSQL **18.7**, pg_search **0.26.1**, native Linux ARM64, Rust **1.99.1**.
Each value below is the median client wall time in **milliseconds** for the entire
workload (20,000 conversions or 2,000 searches), with JIT and PostgreSQL parallel

## Interpretation

Constant pattern evaluation is **52.74% faster** than the old dependency and
54.04% faster than the dependency-only control. This comes from the volatility
correction, not a faster tokenizer: a separate `EXPLAIN (VERBOSE)` check shows
the final plan output as `'{w.*,h.*,h.*}'::text[]`, whereas the old STABLE function
remains a function call. The row-dependent parser is **1.70% slower** by median.

Complete ranked search is **3.62% slower** by median. The final build is slower
in all three paired rounds (2.20%, 3.62%, 14.76%); this run does not establish an
end-to-end gain. The dependency-only control varies substantially too. Do not
infer that the tokenizer change explains the full-query timing difference.
Median per-round search p95 is 0.960 ms (old), 1.196 ms (dependency only), and
1.012 ms (final); median throughput is 1,487 / 1,261 / 1,435 queries per second.

Scalar word conversion has a 7.32% lower median, but its final third round is
slower than the baseline. Array conversion is effectively unchanged (+0.23%).
COPY has a 2.91% lower median with overlapping ranges. These small differences
are observations from three rounds, not a general throughput guarantee.

## Remaining Performance Work

1. Prefer the existing document-batch/COPY path for imports: final warm
   `batch_512` is **8.59x** faster than scalar word conversion for the same
   output, even including grouping, array construction and output checksums.
   This batch optimization predates the dependency upgrade.
2. Profile scalar dictionary validation next. `with_dictionary_cache` reads
   the live version/xmin via SPI on every scalar call; a document batch does
   that once per batch. An explicitly frozen dictionary API for generated
   columns could remove that cost and offer truthful immutable semantics.
   Keep live-table behavior separate; do not hide updates in transaction caches.
3. Measure repeated query planning/prepared statements separately, preserving
   real Top-K plans and exact scored hits. The synthetic dynamic parser is under
   1 microsecond/document here, so parser tuning alone has limited room to
   improve an approximately 0.7 ms complete search.

## Correctness And Setup

Each variant/round creates a fresh UUID database, connections and indexes.
Variant order rotates across rounds. Conversion methods also rotate; each
aggregate records its first backend call, runs a complete warmup, then measures
a complete consumed output. Ranked search verifies every scored hit outside
timing, warms all 2,000 queries and measures the Top-10 client queries with
automatic statement preparation disabled. COPY uses a stored generated pinyin
column and an already-created BM25 index, and includes upload and commit.

All nine runs match 20,000 source-dictionary word outputs, the independent
pronunciation fixtures, `whh -> ['w.*','h.*','h.*']`, and every scored hit and
Top-K result. There are 5,367 complete scored hits per 2,000-query set. Real
ParadeDB Top-K Custom Scan plans are present. All search indexes are
**3,350,528 bytes**; all COPY-created indexes are **3,391,488 bytes**. No index
size improvement is claimed. Memory pressure counters do not increase during
the benchmark. CPU/IO counters and all plans remain in the raw report.

Warm versus first-backend aggregate medians for scalar word conversion:
246.098 / 335.739 ms (old), 235.852 / 297.867 ms (dependency only), and
228.094 / 321.889 ms (final). First-backend search medians are 3.007 / 2.448 /
3.150 ms, respectively; these include connection-local initialization, not an
OS-cache flush.

Validation passed: 35 Rust unit tests; strict Clippy for the non-extension lib;
22 data-import tests and 9 dictionary-accuracy tests; 208 Python tests including
real install/upgrade and standalone SQL backends; 1,588 pgTAP assertions on PG18;
40 core pgTAP assertions on PG19rc2, including real read-only parallel workers.
PG18/PG19 `pg_test` feature checks and the benchmark binary check pass. The
generated-column negative control fails on the genuine 0.0.8 catalog with
SQLSTATE 42P17 and passes after the 0.0.9 migration.

Local image builds used the cached `pg-pinyin-test:pg19beta4` image as a build
base after upstream HTTP package downloads failed, then installed/upgraded the
actual PG18.7 and PG19rc2 server and header packages from the official HTTPS
PGDG repository. The tested versions above were read from the running servers.
This is not evidence of a clean default-base Docker build, x86_64 validation,
PG15-17 testing or a PG19rc2/pg_search integration run. PG19 validation is core
only. The extension remains development version 0.0.9; no release bump.

## Reproduction

Use the separately rebuilt/installed libraries identified by the variant
manifests retained with the local raw report, with each matching cargo-pgrx
version and `--release --no-default-features --features pg18 --locked`. Alias
each installed library under its manifest name before installing the final
catalog and current migration SQL. Export the raw report's `variants` list to
a manifest on that same local server, then run:

```bash
python3 scripts/benchmark_pgrx_upgrade.py --dsn "$PGADMINURL" \
  --manifest /path/to/variants.json --rows 20000 --queries 2000 --rounds 3 \
  --output /path/to/new-report
```

The script verifies the server-side library SHA256 and refuses to overwrite
existing reports. Source/dictionary/compiler/library hashes and installation-SQL
hashes are included in the raw report. Fresh databases do not isolate shared
OS caches or unrelated host activity. No owned builds ran during measurement.

Times are client wall milliseconds per complete workload, not isolated Rust CPU.
First-backend aggregate includes initialization; it is not a cold OS-cache measurement.
COPY includes first-use conversion, indexed writes, upload and commit; it is not warm conversion CPU.
Constant parsing intentionally measures planner constant-folding separately from dynamic inputs.
Fresh databases prevent collisions, not shared OS caches or external host load.
No business-ranking or index-reduction improvement is inferred from output parity.
